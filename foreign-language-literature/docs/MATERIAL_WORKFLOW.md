# 教材制作ワークフロー

## 調査結果と適用範囲

調査対象は `foreign-language-literature` 以下のReact/Viteアプリです。従来は作品・章の管理処理がなく、Supabase REST APIは認証のみに使用されていました。教材、共通辞書、進捗、文ごとの編集フォームはlocalStorage保存でした。旧PrismaモデルはUUIDの正規化テーブルを想定していますが、アプリの教材IDは任意の文字列であり、そのまま結びつける保存処理はありませんでした。

今回、読書画面の構成・クイック翻訳を維持し、教材制作画面とローカル管理を更新しました。既存教材の削除・実DBへの接続・SQLの実行・データ移行・公開は行っていません。

## 原文を参照する編集画面

- 左側に原文プレビュー、原文入力、日本語訳、英語訳、前後移動、保存を配置。詳細を切り替えても参照できます。
- 右側は語彙・文法・構文・備考・新規文。スマートフォンでは縦配置になり、詳細編集側に原文の参照表示を置いています。
- 「変更を保存」「文の変更を保存」は原文・翻訳・構文・備考をまとめて現在文に反映します。辞書と文法事項には個別の保存操作があります。
- 訳が未入力の場合は欄の下に表示します。入力中は文ごとにローカル下書き保存し、別の文への移動・再読込後にも復元します。

## 原文から語彙を登録する

- 原文の語をクリックすると既存の登録情報を読み込み、未登録語なら空のフォームを開きます。意味の推測・自動保存はしません。
- 下線が登録済み、点線が未登録。編集画面内だけの表示です。元の原文・空白・句読点は維持します。
- クリック可能な未知語の分割には端末標準の `Intl.Segmenter` を使用します。登録済みの複数語表現は先に対応付け、最長一致を優先します。
- 原文をドラッグ／キーボードで範囲選択し、「選択した語句を登録」で複数語を登録できます。登録後は文のtokensにも表現を追加し、読書側のクイック翻訳・文法参照と連携します。
- `lemma`（辞書形）と `partOfSpeech`（品詞）を任意項目として追加しました。たとえば `est` の辞書形に `être` を指定すると、同じ言語の `être` の登録済み情報を参照します。形態の自動推定は行いません。表層形に個別の訳があればそちらを優先します。
- 性・語源・文法参照・苦手フラグも編集できます。苦手フラグは学習進捗であり、共有する教材には含みません。
- 辞書形への参照は1段階です。循環参照をたどったり、自動で語形を補完したりはしません。

## 作品と章

ライブラリの「作品・章を管理」を開きます。編集権限のあるログインが必要です。

- 作品: 作成、作品名・著者・原文言語の変更、上下への並び替え、削除。
- 章: 作成、タイトル・解説の変更、上下への並び替え、削除。
- 空の作品・空の章も保存できます。全作品を削除した場合も、再読込でサンプル作品を勝手に復活させません。
- 並び順は既存の配列順を維持します。既存IDを変更しません。新規IDは接頭辞付きUUIDです。
- 言語を変更する場合は、共通辞書の参照先が変わることを確認します。従来の辞書を削除・移行しません。
- 削除は確認を経て、保護コピーを保存してから行います。クラウドや共有版へは自動反映しません。

## 長い本文を登録する

「作品・章を管理 → 本文一括登録」を使います。

1. 対象作品と、新しい章／既存章の末尾を選択。
2. 原文を貼り付けて「文に分割してプレビュー」。
3. プレビューの各文を修正。次の文と結合、カーソル位置で分割、不要な候補を除く操作も可能。
4. 「確定して登録」で確認して保存。ライブラリに反映します。

略語（M., Dr., z. B.など）、小数、引用符、会話文の話者節、省略記号、段落を考慮した保守的な候補生成です。文学の句読法を完全には自動解析しないため、プレビュー確認が必要です。20文単位で表示し、プレビューのIDを確定時も使います。同じプレビューの重複ID・同じ新規章IDを拒否し、確定後は再登録できなくします。新しい登録は「別の本文を登録」で始めます。

作成途中の本文とプレビューもブラウザへ保存します。保存容量には上限があるため、長編は章単位で登録してください。容量不足なら元の教材を保ち、処理を中止します。

## 保存先の区別

| 状態 | 内容 | 閲覧範囲・反映 |
| --- | --- | --- |
| フォーム下書き | 未反映の本文・訳・語彙・文法入力 | このブラウザ内のみ |
| ブラウザの教材 | 保存操作で反映した教材本体と共通辞書 | 同じブラウザの読書画面。アカウント間でも共通 |
| Supabase非公開保存 | ブラウザの保存済み教材のスナップショット | RLSで編集者本人のみ |
| 共有版 | 非公開保存のうち、明示的に共有した版 | RLSでログイン済み閲覧者に限定 |

下書きと学習進捗、認証情報はクラウド教材に送信しません。自動アップロード・自動公開はありません。「保存と共有」で状態を取得し、非公開保存／共有を別々に行います。共有は確認ダイアログを経ます。フォームの下書きは先に教材本体へ保存してください。

今回の保存・共有単位はライブラリ全体（全作品と共通辞書）です。共有操作時にもこの範囲を確認します。作品単位の公開先選択や、招待した閲覧者だけに限定する共有は次段階の機能です。

別端末へは「Supabaseの状態を確認 → Supabaseから復元」。他の作成者の共有版は作成者UUIDを入力して明示的に読み込みます。読み込み前に現在の教材を保護します。クラウドの行はrevision条件付き更新とし、他端末が先に更新した場合は上書きせず、再取得を求めます。

## 保護とバックアップ

- 削除、一括登録、バックアップ／クラウドからの読み込みの前に、直前の教材・辞書・文の下書き・語彙下書き・一括入力・ライブラリフォーム・進捗を `rsl-react-recovery` へ保存します。直前の1件です。
- 「作品・章を管理 → データ保護」から復元できます。復元の直前の状態も保護し、復元の途中で書き込みが失敗した場合は元の組み合わせへ戻します。
- 教材・辞書の書き込みも、片方に失敗した場合は元に戻します。保護コピー自体を作れない場合は削除・登録を進めません。
- クラウドの既存版を更新する場合も、直前の取得済み版をブラウザに保護します。容量不足ならアップロードを中止します。
- JSONバックアップは従来の `app/version/data/dict/progress` を維持し、任意の `drafts/vocabularyDrafts/bulkDraft` を追加しました。旧ファイルも読み込めます。認証トークンは含みません。
- 保護コピーは同じ端末内のものです。ブラウザのデータ削除・ディスク故障には備えられないため、作業の節目でJSONを書き出してください。

## 互換性

`Work.author`、`Token/DictEntry.lemma`、`Token/DictEntry.partOfSpeech` はすべて任意項目です。古い教材を一括変換しません。既存のID・章順・構文ステップ・翻訳形式・下書きキーを維持し、追加フォーム項目だけ空文字で補完します。従来の正規化テーブル、認証API、既存RLSは変更していません。

## Supabaseの追加SQL：本番の最終確認待ち

現在の最終レビュー・SQL手順は [Supabase適用前レビュー](SUPABASE_RELEASE_REVIEW.md) を参照してください。DB側でのrevision/updated_at管理、全階層のJSON許可リスト、事前監査の指紋チェックを追加しました。本番のSQLは未実行です。

コードとSQL案は用意しましたが、実DBには未適用です。未設定時には「教材保存テーブルが未設定」と表示し、ブラウザのデータを保持します。

- `supabase/material-workflow.sql`: 新規2テーブルと、そのテーブルだけに作用する権限・RLSをトランザクションで作成する案。
- `public.reading_studio_drafts`: 編集者UUIDを主キーとし、本人のみ読み書き可能なJSON教材スナップショット。
- `public.reading_studio_publications`: 非公開データと別の共有用スナップショット。読み取りはログイン済みユーザー、書き込みは作成者本人かつ既存 `public.is_editor()` 判定を通る編集者。
- 既存テーブルのALTER/DROP、既存データの移行・削除、Authテーブルの変更は含みません。サービスロールキーも使用しません。
- `prisma/schema.prisma`: 対応するモデルをローカルで追加済みです。`supabase/material-workflow.prisma.proposed` は参照先を示す旧ファイルです。DBへは未適用です。

承認後の手順案:

1. Supabaseの既存データ／スキーマと `public.is_editor()` を読み取り確認。
2. ローカルのPrismaモデルと最終SQLを照合し、事前監査の指紋を設定して最終承認。
3. 承認されたSQLを実行。既存テーブルが同名なら、勝手に変更せずトランザクションを中止。
4. 実ユーザーで本人保存・他ユーザーの非公開アクセス拒否・共有版閲覧・非編集者の書込拒否を検証。

**この追加SQLを `prisma db push` で代用しないでください。** RLSはPrismaモデルだけでは設定されません。モデル案を適用せずに新テーブル導入後の `db push` を実行すると、Prismaが未定義テーブルの削除を提案する可能性があります。

JSONスナップショット方式は、既存の文字列ID・配列順・任意項目を保ち、複数テーブルへ途中まで保存される問題を避けるためです。旧正規化テーブルに手動入力した内容の移行は行いません。

## 検証

```sh
npm test
npm run build
npm run lint
```

ブラウザテストはREADMEと同じ一時フォルダのPlaywrightを使用します。

```sh
PLAYWRIGHT_MODULE=/tmp/reading-studio-qa/node_modules/@playwright/test/index.mjs npm run test:workflow
PLAYWRIGHT_MODULE=/tmp/reading-studio-qa/node_modules/@playwright/test/index.mjs npm run test:ui
PLAYWRIGHT_MODULE=/tmp/reading-studio-qa/node_modules/@playwright/test/index.mjs npm run test:quick-ui
```

`test:workflow` は隔離ブラウザ内で、原文参照、語彙の直接登録、複数語の範囲指定、辞書形参照、翻訳・構文・文法、下書きの文移動／再読込、作品・章・一括登録・並び替え・削除・復元・認証の出入り・スマートフォンを検証します。クラウドはモックAPIで非公開／共有の分離と競合を検証し、実DBには一切変更を加えません。

残る確認: 追加SQLの承認と適用、実SupabaseでのRLS検証、Safari/iPadの実機、非常に長い章での端末ごとの容量と速度です。
